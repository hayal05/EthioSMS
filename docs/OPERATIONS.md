# Pilot deployment and operations

## Deployment gate

Repository work and simulated tests do not create a running service. No Render/Neon project, phone credential, live SMS configuration, or deployment has been activated. The owner must choose/provide infrastructure and approve deployment/live testing. Implementation pull requests #1–#12 are merged into main.

The [Render blueprint](../render.yaml) provisions ONE free web service only when manually imported and deployed. It targets main, which contains the merged pilot implementation. Automatic deployment is disabled. Reference: [Render blueprint specification](https://render.com/docs/blueprint-spec).

## Configure and start a mock pilot

1. Create a Neon project/branch for the pilot. Store the pooled PostgreSQL URL privately as DATABASE_URL; use verified TLS. Keep the database close to the backend region if available. Do not point TEST_DATABASE_URL at Neon or production.
2. Generate independent random 32-byte hexadecimal secrets for PAYLOAD_ENCRYPTION_KEY and OTP_SECRET using the command in .env.example. Keep secure backups. Render's generated secrets are base64, so do not use generateValue for these two hex-only variables. READINESS_TOKEN may be generated by Render.
3. Import render.yaml only after deployment approval, or configure the same values manually. Build: `npm ci --include=dev && npm run build`; start: `npm start`. The production backend serves the built frontend. Keep SMS_GATEWAY=mock, SMS_ENABLED=false, LIVE_SMS_APPROVED=false. Secure cookies require HTTPS. Trust exactly the known Render proxy, not arbitrary forwarded headers.
4. Before inviting users, run `npm run db:migrate` in a trusted environment with the SAME private database URL, then open the empty installation and create the master admin using email, password and confirm password. No setup key is required. Free Render need not provide a shell: migrations can run using the manual GitHub migration workflow or on the owner's trusted computer. The offline bootstrap remains an optional operator path. Never put secrets in a build command or commit.
5. Visit HTTPS site, set administrator password, create/approve an application, issue a scoped key and verify mock submissions. Dispatch starts PAUSED. Unpause only after reviewing the intended queued work. Add 2–5 invited users after the owner-only mock checks pass.
6. Configure an uptime monitor on GET /health. It deliberately does not query Neon or contact the phone. Use authenticated /api/ready for manual database readiness checks; never expose its token in a public monitor URL.

Render Free can sleep/restart and has shared monthly allowances; an uptime bot is not an uptime guarantee. Sleeping delays dispatch/expiry/retries and cold starts can outlast an OTP's useful life. Known-work timers are best effort. Startup, a new submission, or the authenticated drain control resumes recovery. Review [Render free limits](https://render.com/docs/free) and [Neon plans](https://neon.com/docs/introduction/plans) before onboarding. Upgrade the backend for reliable paid/public OTP delivery. A continuously active database may exhaust Neon free compute; watch usage. No separate free background worker is assumed.

## Maintenance and retention

Run `npm run db:maintain` from a trusted terminal with the configured DB, or use the administrator Operations control (POST /api/admin/maintenance). This is deliberate, not a continuously polling background service. During the pilot run it at least daily and check counters; repeat bounded passes when a backlog remains. It expires up to 100 queued jobs' recipients, releases unsent quota, wipes obsolete OTP payloads, removes expired sessions/setup tokens/old rate buckets, purges up to 50 old settled message jobs and their dependent campaign/attempt/OTP records, and trims old audit/usage records. Unknown/accepted outcomes are not resent.

Defaults: message history 30 days, expired OTP metadata 24 hours, audit 90 days. PATCH /api/admin/retention with JSON messageDays (1–365), otpHours (1–168), auditDays (1–730) adjusts these. Shortening retention can irreversibly remove old records on the next maintenance run. Quota counters with reserved usage are retained; active/unsettled work is not silently discarded. Suppressions persist until separately reviewed consent procedures are implemented. Use moderate campaign/contact volumes; this is a small pilot.

## Backup and restore

Before migrations and periodically during the pilot, create a private PostgreSQL custom-format dump from the direct Neon endpoint using `pg_dump --format=custom --file=ethiosms-backup.dump`. Supply credentials through a private PGPASSFILE/secure connection environment, not command-line secrets or repo files. Store the dump encrypted with access restricted to the owner. Back up PAYLOAD_ENCRYPTION_KEY and OTP_SECRET separately: database dumps alone cannot decrypt payloads or validate existing challenges.

Restore only into a NEW empty isolated database/Neon branch using `pg_restore --no-owner --no-acl --dbname=RESTORE_DATABASE ethiosms-backup.dump`, with the restore connection supplied privately. Verify migration checksums, account access and read-only history before switching traffic. Keep dispatch PAUSED and live flags OFF throughout restore verification; a restored outbox may contain already-processed messages. Never unpause an old backup without reconciling recipient/provider IDs against current delivery history. Do not restore over the active pilot DB. The migration ledger is public.ethiosms_migrations and application data lives in schema ethiosms.

## Rollback and recovery

Pause dispatch; record the running commit, migration ledger and affected message IDs. Roll back code only if its schema expectations remain compatible; otherwise prepare a forward corrective migration or restore to an isolated branch first. Never edit an applied SQL migration. Retain stable event IDs when retrying requests. Lost leases and ambiguous transport results become unknown and count conservatively; inspect provider status before any new replacement send. Pausing cannot undo a request already in flight. Recover the administrator only through the documented trusted CLI.

## Monitoring

Logs intentionally omit bodies, phone numbers, secrets and raw provider/DB errors. Review safe failure codes, queue counts, reserved/used segments, DB storage/compute, and last successful gateway API contact. That contact is not proof the device is online. Protect Render/Neon/GitHub accounts and server environment access. No incoming SMS webhook/automatic STOP endpoint is exposed; record campaign opt-outs manually.

A minimal opaque request-history ledger is retained beyond message purging to prevent old retries from resending. It contains tenant/application IDs, opaque event key, keyed fingerprint, original message UUID and timestamp, not message content. Include it in backups. Do not delete it or replay old outbox events after restore without reconciliation. API callers should never put personal data in event keys.
